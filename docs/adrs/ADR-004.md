# ADR-004: Product-create mechanism — hand-rolled Open API flow (A13)

- **Status:** Accepted (decision made on documented + live-verified evidence; the
  MCP live spike was not required and is superseded — see "Why no live MCP run")
- **Date:** 2026-09-15 (proposed 2026-09-14)
- **Deciders:** Founder (CEO) — chose the hand-rolled Open API on 2026-09-15
- **Context PBI:** PBI-026 (`specs/fourthwall-integration/spec.md`, contract C2)
- **Related:** ADR-005 (read path), PBI-014 (`nodes/fw_create.py`), PBI-027 (cutover)

## Context

The pipeline's FW-create node (PBI-014) drafts products through an injected
client with a hardcoded DRAFT payload. For the v1 publish cutover (PBI-027) we
must settle the single write path (CC-2): the official Fourthwall MCP
product-create tool, or a hand-rolled Open API flow.

ADR-004 was originally conditional on a **live MCP spike** against the placement
matrix. That spike requires an authenticated MCP session, and ADR-005
established by live discovery that `https://mcp.fourthwall.com` is
**OAuth-2.0-interactive-only** (authorization_code + PKCE + mandatory dynamic
client registration; no static credential, no `client_credentials` grant). So
"H1 — run the MCP spike with the configured token" was not reachable in this
environment without first building an interactive OAuth connect flow.

Meanwhile the Platform Open API write path turned out to cover the whole matrix
on documented evidence, authenticated by the shop API user we already hold.

## Decision

**v1 ships the hand-rolled Platform Open API flow** for product-create,
implemented once behind the pipeline's injected Fourthwall interface. No MCP
write calls in production.

Documented mechanism (`docs.fourthwall.com`, verified 2026-09-15):

1. `GET  /open-api/v1.0/product-templates` → pick `productTemplateId`.
2. `POST /open-api/v1.0/media/upload-url` → `{uploadUrl, fileUrl}` (send exact `size`).
3. `PUT  <uploadUrl>` (directly to GCS; **no** Fourthwall credentials) with
   `Content-Type` matching step 2 and `x-goog-content-length-range: 0,<size>`.
4. `POST /open-api/v1.0/media/images` → `{id}` = **`imageId`** (register once,
   reuse per region/product).
5. `POST /open-api/v1.0/products` with `type: "design"`, `productTemplateId`,
   `regions: [{region, imageId, placementStrategy}]`, optional
   `colors`/`sizes`/`profitMargin`, and **`publishOnCreate: false`**.

Matrix mapping (the evidence the spike was meant to produce):

| Placement-matrix concern | Open API field |
|---|---|
| front/back/sleeve region | `regions[].region` |
| placement strategy per region | `regions[].placementStrategy` ∈ `AUTO`, `FILL_ALL`, `FULL_REGION`, `PLACEMENT_ID` |
| colorways | `colors` (per-region filter) |
| multi-region in one product | multiple `regions[]` entries, one `imageId` each |
| DRAFT-first (PBI-014 behavior) | `publishOnCreate: false` (default hidden) |
| price | `profitMargin` (USD) on top of base cost — Shelf invariants still gate the write |

Auth: the shop **Open API user** (HTTP Basic). Fourthwall's docs state API keys
have **full access** to these endpoints (OAuth scopes `offer_write`/`media_write`
apply only to multi-shop OAuth apps), so no OAuth flow is needed for writes.

## Why no live MCP run

The spike's purpose was to *decide under uncertainty*. The uncertainty is gone:
- the MCP write surface is reachable only via an interactive OAuth connect flow
  (ADR-005 evidence) — a large, deliberate build;
- the Open API covers every placement-matrix concern on documented evidence
  (table above), with credentials already in hand.

Running the MCP spike would therefore have required *building the losing
alternative* first. The decision is recorded on that evidence instead.
`scripts/fw_create_spike.py` is retained for history but **superseded**: its
`CREATE_TOOL_CANDIDATES` (`create_product`, `products_create`,
`create_draft_product`) match no real MCP tool (the real ones are
`ecommerce_create-digital-offer`, `ecommerce_create-offers-from-designs`,
`ecommerce_update-offer`), so a `--live` run today would report a false
negative. Do not treat its output as evidence.

## Consequences

- **PBI-027 is unblocked.** It implements exactly this Open API flow behind the
  existing injected interface; the MCP write path is not built.
- **PBI-014's interface is unchanged** — only the injected client's
  implementation lands in PBI-027, preserving the DRAFT-first contract.
- Shelf price invariants are still enforced **before** the write call (C6), and
  `profitMargin` is derived from the shelf/contract at the call site, never a
  literal.
- Credentials reuse the read path's API user (HTTP Basic); no new secret type.
- No second write path: `POST /open-api/v1.0/products` is called from exactly one
  place (`nodes/fw_create.py`'s client). CC-2 holds.
- `imageId` registration is cacheable across products/regions — an efficiency
  win the MCP surface would have hidden.

## Alternatives considered

- **MCP write tool.** Rejected: requires an interactive OAuth connect flow to
  even attempt, for no documented coverage the Open API lacks.
- **MCP write unconditionally** (original ADR-004 H1). Rejected: assumption
  without reachable evidence (spec anti-pattern).
- **Hybrid, routed per case.** Rejected: second write path (CC-2 violation).
