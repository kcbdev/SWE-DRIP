# ADR-003: Auth architecture — Better Auth runtime + FastAPI validation + same-origin API

- **Status:** Accepted
- **Date:** 2026-09-13
- **Deciders:** Founder (CEO)
- **Context PBI:** PBI-004 (`specs/auth-rbac/spec.md`)

## Context

The Control Panel needs multi-user, session-based auth with three roles
(`admin`, `operator`, `viewer`) enforced server-side. Two runtimes exist — a
Next.js frontend and a FastAPI backend — and the spec forbids a second auth
system. We must decide who owns credentials/sessions and how the Python API
learns the caller's identity and role without trusting client-supplied data.

## Decision

1. **Better Auth is the sole auth runtime**, living in `control-panel/` with the
   Postgres adapter. It owns the `user` / `session` / `account` tables and the
   session cookie. Public signup is disabled (`disableSignUp: true`); users are
   invited by an admin. The `admin` plugin supplies the `role` field with
   `adminRoles: ["admin"]` and `defaultRole: "viewer"`.
2. **FastAPI never issues credentials.** It validates sessions only:
   - read cookie `better-auth.session_token`, whose value is
     `"<token>.<signature>"`;
   - verify the signature as **base64url(HMAC-SHA256(BETTER_AUTH_SECRET, token))**
     using a constant-time compare;
   - look the raw `token` up in the `session` table, check `expiresAt`, and join
     `user` to resolve `email` + `role`.
   No session → 401; role not permitted → 403 (enforced by `api/app/rbac.py`).
3. **Browser traffic is same-origin `/api/*`.** The frontend calls its own
   origin for both `/api/auth/*` (Better Auth) and the FastAPI endpoints. In
   local dev a Next.js rewrite proxies `/api/*` to the FastAPI process; in
   production Traefik path-routes `/api/*` to the API. This keeps the session
   cookie first-party and avoids CORS/token-in-JS.
4. **Roles are the exact strings** `admin`, `operator`, `viewer` in the DB, the
   API, and the UI. No aliases.

## Consequences

- A second auth system (Python sessions/JWT, social SSO) is an ADR-gated change.
- The cookie signature format is a contract: if Better Auth changes it, this ADR
  is updated with the verified mechanics before code changes.
- Integration verification (sign in, `/api/me`, 403 for viewer on admin routes)
  requires Postgres; unit gates stay offline via pure-function signature tests
  and a dependency-overridden role matrix.

## Alternatives considered

- **FastAPI-native sessions/JWT** — rejected: violates the single-runtime rule
  and duplicates credential handling.
- **Trusting a client-sent role header** — rejected: insecure; identity must be
  resolved server-side from the signed session.
- **Cross-origin API with cookies + CORS credentials** — rejected: more surface,
  fragile cookies; same-origin path routing is simpler and safer.
