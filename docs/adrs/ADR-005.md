# ADR-005: Fourthwall read path — Platform Open API (Basic Auth), not the MCP server

- **Status:** Accepted
- **Date:** 2026-09-15
- **Deciders:** Founder (CEO)
- **Context PBI:** Fourthwall integration (reads); supersedes the read half of
  Vision doc §4 and revises `specs/fourthwall-integration/spec.md` contract C1

## Context

Vision doc §4 selected "the official Fourthwall MCP server
(`mcp.fourthwall.com`, OAuth2)" for reads, and `specs/fourthwall-integration/spec.md`
recorded the v1 lifecycle as "token supplied via server env
(`FOURTHWALL_MCP_TOKEN`) with documented refresh procedure". The deployed
integration used `FOURTHWALL_MCP_URL=http://host.docker.internal:3100` +
`FOURTHWALL_MCP_TOKEN=<string>`, and `/api/catalog` failed with
`list_products failed: unhandled errors in a TaskGroup (1 sub-exception)`.

Live verification (2026-09-15) of every assumption behind that decision:

| Assumption | Evidence |
|---|---|
| An MCP endpoint existed at the deployed URL | `host.docker.internal:3100` served nothing |
| The official MCP accepts a static token | `GET https://mcp.fourthwall.com` → `401` with `www-authenticate: Bearer resource_metadata="…/oauth-protected-resource"` |
| A static token can be minted out-of-band | `/.well-known/oauth-authorization-server` → `grant_types_supported: ["authorization_code","refresh_token"]` — **no** `client_credentials`; `code_challenge_methods_supported: ["S256"]`; `registration_endpoint: https://mcp.fourthwall.com/oauth/register` (dynamic client registration required) |
| The tool names in `client.py` existed | Docs list the MCP tools as `ecommerce_get-offers`, `ecommerce_get-orders`, `ecommerce_get-*-report`, … — not `list_products`/`get_product`/`list_orders`/`get_analytics` |
| The credentials in hand were MCP tokens | They authenticate the **Platform Open API** (`https://api.fourthwall.com`), verified `200` on `/open-api/v1.0/shops/current`, `/products`, `/order`, `/collections` |

So the MCP path is **OAuth-2.0-interactive-only** (browser login + PKCE + token
refresh). It cannot be satisfied by the configured static credential, and a
deployment runbook cannot "refresh" it.

Equally important: a code trace showed this codebase only ever calls
`list_products`, `get_product`, and `list_orders` (`get_analytics` was defined
but unused), and `analytics.py` derives every KPI from **orders**. Those three
reads all exist on the Open API, which the shop-level API user already
authorises. The MCP's unique value — its report tools — is not used.

## Decision

Fourthwall **reads** go through the **Fourthwall Platform Open API** over HTTPS
with HTTP Basic shop credentials:

- Base URL `https://api.fourthwall.com`; products `GET /open-api/v1.0/products`
  (+ `/{productId}`), orders `GET /open-api/v1.0/order` (paged
  `{results,total,page,size,totalPages}`).
- Auth `Authorization: Basic base64(username:password)` using a shop
  **Open API user** (`FOURTHWALL_API_USERNAME` / `FOURTHWALL_API_PASSWORD`),
  created by a SUPER ADMIN under Settings → For developers.
- Credentials are server-side only, admin-configurable in Settings →
  Integrations, and never returned by the API (presence only) — C7 is preserved
  in spirit; the store is server-side, not the frontend.
- Field normalization lives at the single integration boundary
  (`api/app/fourthwall/client.py`): `state.type` → `status`,
  `variants[].unitPrice.value` → `price`, `amounts.total.value` → `total`,
  `createdAt` → `created_at`.

The MCP server is **not** used for reads in v1. It remains the only surface
that exposes Fourthwall's report tools and its write/design tools (see
ADR-004), so a future PBI may add an MCP **OAuth connect** flow behind the same
`FourthwallReadClient` interface if/when report data is actually needed.

## Consequences

- Reads work today with credentials already in hand; `/api/catalog`,
  `/api/analytics/*`, and the webhook trigger stop degrading.
- The price-invariant check becomes meaningful: category is keyword-derived from
  the product `name`/`slug` (Fourthwall has no category field — its `type` is
  only STANDARD/GIFT_CARD/UNKNOWN), and price comes from the first variant's
  `unitPrice`. Products whose name carries no tee/hoodie/mug keyword stay
  explicitly `unmapped` rather than guessed.
- `scripts/fw_create_spike.py` and ADR-004 keep their MCP framing and remain
  **pending** — writes are a separate decision. Note for that spike: the real
  MCP write tools are `ecommerce_create-digital-offer` /
  `ecommerce_create-offers-from-designs` / `ecommerce_update-offer`, not the
  `create_product`/`products_create`/`create_draft_product` candidates the
  harness currently looks for.
- Deploy env changes: `FOURTHWALL_MCP_URL`/`FOURTHWALL_MCP_TOKEN` are retired in
  favour of `FOURTHWALL_API_BASE_URL`/`FOURTHWALL_API_USERNAME`/
  `FOURTHWALL_API_PASSWORD` (or nothing at all, when set via the Settings UI).

## Alternatives considered

- **Implement the MCP OAuth flow (DCR + PKCE + refresh + a Connect button).**
  Correct and spec-faithful, but strictly more machinery for capability we do
  not call, and it needs an interactive browser login per shop. Deferred, not
  rejected.
- **Keep the MCP path and hand-mint a long-lived token.** Not possible — the
  server offers no such grant.
- **Scrape the public storefront JSON feed.** Rejected: undocumed shape,
  no order data, and a second unofficial path.
