# PBI-043: Operator token auth for machine clients

## Directive

Machine clients cannot use Better Auth cookies, so give them scoped Bearer
tokens without weakening auth:

1. Migration `api/migrations/0007_operator_tokens.sql` — `operator_tokens(token_hash PK, prefix, name, scopes text[] / comma string, created_by, revoked_at, last_used_at, created_at)`. Append-only + revocation flag; no update path for the hash.
2. `api/app/operator_tokens.py` — `issue_token(name, scopes, actor)` returns the plaintext **once** (`sdr_` + 32 random bytes; store `sha256(salt + token)`), `verify_token(plaintext)` → token record or None (constant-time compare, updates `last_used_at` best-effort), `revoke_token(prefix/id, actor)`. Unknown scope rejected; allowed scopes are exactly `read`, `operate` (`operate` implies `read`).
3. `api/app/routers/operator_tokens.py` — Admin-only: `POST /api/operator-tokens` (issue, audited, plaintext in response once), `GET /api/operator-tokens` (metadata only — hash/prefix, never values), `POST /api/operator-tokens/{id}/revoke` (audited). Viewer/Operator get 403.
4. A FastAPI dependency `require_token(scopes)` for the MCP mount (PBI-044 consumes it): Bearer parse, revoked/unknown → 401, insufficient scope → 403. Cookie/session auth is never consulted on token paths.

Scope boundaries: no MCP tools here (PBI-044/045); no OAuth/DCR; token values never enter logs, errors, or audit rows (prefix/hash only).
