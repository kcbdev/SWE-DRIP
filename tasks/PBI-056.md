# PBI-056: Styles management API (list + create + edit, audited)

## Directive

Manage the PBI-048 style repo through REST so PBI-052 has a UI to talk
to (all writes Admin-only + audited; reads Viewer+):

1. `GET /api/styles` → `{version, styles: [{name, graphic_definition}]}` through `pipeline/styles.py` (single source). A missing/malformed repo
   is a loud 503 with the reason, never a 500 and never a fallback list.
2. `POST /api/styles {name, graphic_definition}` → 201: name-uniqueness
   enforced (409 on duplicate, exact match), both fields non-empty,
   atomic write (tmp + replace, like the collections store), `version`
   bumped. Concurrency via `expected_version` (409 on mismatch — the
   mtime discipline, not last-writer-wins).
3. `PATCH /api/styles/{name} {name?, graphic_definition?}`: rename and/or
   redefinition, same validation + audit + version bump. No delete:
   the locked repo only grows; DELETE returns 405 loudly (deletion would
   strand approved contracts).
4. C1 revalidation surfaced, never silent: every write validates all
   stored contracts' `style_archetype` against the new repo and returns
   `{affected_contracts: [...]}` (contracts that would now fail the
   approval completeness gate). The write still lands — the report is
   the control, not a block — but an empty report reads explicit.

Scope boundaries: no UI (PBI-052); no threshold/prompt changes; no
grandfathering (a rename that strands a contract is reported, the
contract keeps its value until an Admin edits it).
