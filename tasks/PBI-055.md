# PBI-055: Research-run API (trigger + status + logs + gate + board-serve)

## Directive

Expose the PBI-050 collection graph over REST so PBI-052 has a UI to talk
to (all Admin/Operator writes audited; Viewer+ reads):

1. `POST /api/research/runs {collection_slug}` → 202: builds the run
   input from the store (contract v2 + inspiration listing + lineage
   avoid-list via `build_research_inputs`), starts `build_collection_graph`
   background off-thread with the checkpointer, `run_id` = `thread_id`
   (namespaced so research threads never collide with item runs), cost
   guard + audit `research.start` (item-run pattern, no fw_live phase).
2. `GET /api/research/runs` + `GET /api/research/runs/{id}`: status
   derived from visited (`started → synthesizing → board_rendering →
   awaiting_approval → complete | failed`), plus board ref + version,
   `diversity_flags` with reasons, and the gate payload when paused.
   Reads come from the checkpointer — no parallel run store (NFR-1).
3. `GET /api/research/runs/{id}/logs` (+ SSE stream): research nodes
   already emit via `get_logger(cfg)` — wire the Sql logger at start
   (PBI-042 pattern) so rows persist past the first gate.
4. Gate visibility + decision through the existing approvals surface:
   queue scans research interrupts (`collection_gate` payload carries
   draft + board + flags), `build_resume_payload` gains the mapping
   (approve → `{approved: True}`, reject → `{approved: False}`,
   edit-approve via `selection.contract`, validated like the node does),
   `entity_ref` labels the gate. No second approval model.
5. `GET /api/collections/{slug}/board/{ref}`: same-origin board bytes,
   asset-dir-scoped, relative-ref validated (C2 validator reused),
   PNG/JPEG only, loud 404s. Boards render into the asset dir already —
   this only serves them.

Scope boundaries: no UI (PBI-052); no styles endpoints (PBI-056); no
item-graph changes; no auto-approve (gate defaults stay ON).
