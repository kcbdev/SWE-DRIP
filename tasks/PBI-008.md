# PBI-008: Dashboard summary API

## Directive

Implement `GET /api/dashboard/summary` returning: pending approvals count; current-month model spend vs the $130 cap (with >80% flag); active collections count + at-risk flag; recent activity (last N audit events); pending-approval top items (id, type, collection, waiting-since). Create the `model_calls` table migration (`node, model, tokens_in, tokens_out, cost_usd, created_at`) — this PBI owns the migration; the pipeline writes rows later via `pipeline/costs.py`. Read collections by globbing `collections/*.yaml` inline (do NOT create `api/app/collections_store.py` — the collections spec owns the shared store module). Viewer+ role. No writes.

Scope boundaries: no UI (PBI-009); no approvals endpoints (hitl-approvals spec); no KPI time series (catalog-analytics spec).

## Context

- Spec: `specs/dashboard/spec.md`
- Depends on: PBI-006 (audit read path for the activity feed), PBI-004 (RBAC)
- Files/modules touched: `api/app/routers/dashboard.py`, migration files, `api/tests/test_dashboard.py`
- Plane: kcb/SWDRP-8

## Verification

- Contracts C1, C2 (data path), C5 of the spec.
- Executable: `python -m pytest api/tests -q` green (empty-source summary shape; spend rollup math; >80% flag; collections glob with zero/one contract; activity feed maps audit rows).
- Manual (with compose db): call the endpoint with no data → honest zeros/empty states; insert a cost row + a collection YAML → counts update.

## Refinement rule

- If the `model_calls` schema needs fields beyond the data spec §3 cost record (`node, model, tokens_in, tokens_out, cost_usd`), stop and amend the spec's Decisions before altering the table.
- Zero-data responses must be distinguishable from missing/broken sources in the payload shape (explicit nulls vs zeros) — record the chosen convention in the resolution.
